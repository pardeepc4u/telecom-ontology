# Evaluation

> Status: implemented and run live (Phase 6, confirmed 2026-09-20). See
> `eval/` — `questions.py` (the fixed question set), `ground_truth.py`
> (independent, retrieval-code-free ground truth), `metrics.py`
> (precision/recall/F1), and `run_eval.py` (orchestrates + writes the
> table below). Run via `python -m eval.run_eval`.

## Methodology

1. A fixed set of 9 questions spans three categories, each *designed* so a
   different mode should win — not three phrasings of the same question
   (see `eval/questions.py` for the reasoning behind each):
   - **structural_favorable** — pure location lookups ("what tickets are on
     file for tower-032?"), no symptom language for vector search to match.
   - **semantic_favorable** — pure symptom lookups ("have customers
     reported \<exact phrase\>?"), no location for graph traversal to
     resolve an entity from.
   - **hybrid_favorable** — root-cause questions ("what's likely causing
     the outage tickets near router-X?") where the true answer is one
     specific incident cluster, not every ticket near that router (routine
     tickets can land there by chance) and not every semantically similar
     ticket dataset-wide (other incidents reuse similar generic symptom
     language).
2. Ground truth for each question is computed directly from
   `data/generated/{graph,tickets,summary}.json` — never from retrieval
   code — so grading isn't circular. See `eval/ground_truth.py`.
3. Every question runs against all three modes regardless of what the
   router would classify it as: `graph_only` (`structural_ticket_recall`),
   `vector_only` (`vector_retrieval.search`), and `hybrid` (both, fused).
   Scored as set-based precision/recall/F1 of retrieved ticket ids against
   ground truth (`eval/metrics.py`) — order-agnostic, since ground-truth
   sets are small (7–29 tickets) and "did you find the right tickets at
   all" is more legible here than a ranking metric.

## Findings

**Each single-path mode wins decisively on the category built for it**,
exactly as designed: `graph_only` scores a perfect 1.0 F1 on all three
`structural_favorable` questions (the `CONCERNS` edge is a complete,
noise-free index of "what tickets are about this tower," so graph
traversal can't miss); `vector_only` clears `graph_only` by a wide margin
on every `semantic_favorable` question (`graph_only` scores exactly 0.0 on
all three — with no location mentioned, entity resolution has nothing to
resolve, so structural recall can't even start).

**Hybrid did not beat `graph_only` on `hybrid_favorable` questions** in
this run (mean F1 0.53 vs. 0.84) — worth stating plainly rather than
glossing over, since it cuts against the "hybrid is strictly better"
narrative a demo is tempted to lead with. The reason is specific to this
dataset, not a flaw in the fusion mechanism: the synthetic generator
assigns every ticket's `CONCERNS` edge deterministically and correctly at
generation time (`data/generator/tickets.py`), so `graph_only` already has
a near-complete, low-noise signal for "is this ticket about this
location" — there's little room for a second, noisier signal (semantic
similarity, which also pulls in similarly-worded tickets from *other*
incidents) to add net value, and every vector-only ticket it mixes in
dilutes precision. Hybrid still behaved correctly — it fused real evidence
from both paths and ranked overlap highest — it just had less to gain here
because one input was already strong and complete.

This points to hybrid's actual value proposition, which this clean
synthetic dataset understates: it should matter most where the structural
link is missing, inconsistent, or wrong — a mis-tagged `CONCERNS` edge, a
ticket routed to the wrong tower, an ops team that hasn't backfilled
topology metadata for a legacy region — cases real telecom data has and
this generator, by construction, doesn't. A natural follow-up eval:
re-run this same question set after deliberately dropping or corrupting a
fraction of `CONCERNS` edges, and check whether hybrid's F1 degrades more
gracefully than `graph_only`'s. Not done here — flagged as the honest next
step rather than asserted as a result.

**A real bug surfaced and got fixed during this phase, not before it:**
the first evaluation run showed `hybrid` producing *identical* results to
`vector_only` on every `hybrid_favorable` question — structural evidence
was being completely drowned out. Root cause: `fusion.py` originally
summed raw scores from both paths directly, but structural score
(`1/(1+hops)`, giving 0.5 for a one-hop router→tower match) and semantic
cosine similarity (typically 0.55–0.9) live on incomparable scales, so
semantic-only hits routinely outranked genuinely relevant structural hits
that had merely traveled one hop. Fixed by switching `fusion.py` to
Reciprocal Rank Fusion (rank position within each list, not raw score) —
see the module docstring. This is exactly why Phase 6 exists: an eval
harness that runs real questions against real ground truth catches this
kind of bug; eyeballing a couple of demo queries (as Phase 4/5's manual
testing did) did not.
